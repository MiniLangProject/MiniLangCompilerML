# Compiler optimization evaluation — 30 October 2026

The five 1.2.25 optimizations were measured on Windows x64 before changing
the version strings. Python and native ML compilers generated byte-identical
fixture programs. Source and benchmark drivers are in `benchmarks/`; the
semantic, cache and profile gate is `tests/check_compiler_techniques.py`.

## Compiler time and memory

Nine alternating runs compiled `tools/mlfmt.ml` through the monolithic path,
pinned to logical CPU 4. Values are medians. Working set is the OS process
peak, not reserved virtual address space.

| Compiler | Cache | Before | After | Time change | Peak working set before → after |
| --- | --- | ---: | ---: | ---: | ---: |
| Native ML | cold | 1.183 s | 1.186 s | +0.2% | 155.1 → 155.4 MiB |
| Native ML | warm | 0.582 s | 0.537 s | −7.7% | 128.6 → 125.2 MiB |
| Python | cold | 1.860 s | 1.746 s | −6.1% | 61.1 → 61.1 MiB |
| Python | warm | 0.720 s | 0.697 s | −3.1% | 73.1 → 73.3 MiB |

The Python lexer cache activates only for sources of at least 65,536
characters, so this small `mlfmt.ml` fixture measures function-cache behavior
on Python; the integration gate separately checks a large tokenized source.

## Generated-program time and memory

Eleven alternating runs of `benchmarks/runtime_codegen.ml` were pinned to
logical CPU 4. The time is measured inside the program. Heap bytes are the
runtime's bump-pointer growth for that case, not total allocation across GC.
Peak RSS is the operating system process measure. Both compiler
implementations generated the same bytes; separate execution measurements
show normal timing variation.

| Case | Python-built before → after | ML-built before → after | Heap growth before → after |
| --- | ---: | ---: | ---: |
| Three-part string concat | 4.642 → 2.025 ms | 4.636 → 2.102 ms | 8,388,600 → 4,800,000 B |
| Local integer reuse | 8.057 → 5.925 ms | 8.069 → 5.948 ms | 0 → 0 B |
| Indexed byte loop | 6.601 → 5.978 ms | 6.617 → 5.992 ms | 272 → 272 B |

Three-part concatenation peak RSS fell from 15.38 to 11.77 MiB. The other
two cases stayed near 7.15 MiB. Control cases varied by a few percent in
either direction; these optimizations target the specific patterns above.

## Optional PGO

A training run with `--profile-calls` recorded 180,000 calls to a hot
function. Recompiling a 180-call-site fixture with `--pgo-profile` expanded
its hot inline budget from 4,096 to 32,768 bytes. In 15 alternating runs of
the longer fixture, median process time was 283.171 ms without PGO and
280.600 ms with PGO (about 0.9% faster). The executable grew from 365,568
to 381,440 bytes. This small difference is sensitive to process timing;
PGO remains opt-in.

## Correctness

The Windows Python bootstrap and native self-build reached the same compiler
SHA-256. The integration gate exercised normal, empty and mixed string
operations; invalidated local expressions; nonempty and empty byte buffers;
cold/warm lexer cache and damaged-record fallback; call-counter output; PGO;
and Python/native monolithic/MLO byte parity. The incremental regression
suite also passed 96 compilation checks before the version stamp.
